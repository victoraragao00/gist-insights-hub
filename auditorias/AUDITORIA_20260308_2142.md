## VIOLAÇÕES

### CRÍTICO

### ATENÇÃO

**[A1] SearchPage.tsx — Variável usada antes da declaração (linhas 60-61 vs 86)**

```
useEffect(() => {
  if (clientSearchError) toast.error("Erro ao buscar clientes");
}, [clientSearchError]);  // ← linha 60-61
```

`clientSearchError` é declarado na linha 86 (retorno do `useQuery`). Em JavaScript/TypeScript, `const` não sofre hoisting como `var` — está na TDZ (Temporal Dead Zone). Na prática funciona porque o componente inteiro é uma função e os hooks são executados na ordem do React, mas é um **anti-padrão de organização** que pode causar confusão e bugs em refatorações. O `useEffect` que depende de `clientSearchError` deveria estar **depois** da declaração dessa variável.

> **Recomendação:** Mover o `useEffect` (linhas 59-61) para depois da declaração de `clientMatches` (após linha 103).

**[A2] Audits.tsx — Index como key em lista dinâmica (linha 626-627)**

```tsx
{formRecipients.map((r, i) => (
  <div key={i} className="flex gap-2 items-center">
```

A lista de destinatários é dinâmica (adicionar/remover itens). Usar `index` como `key` viola a proibição explícita #10 do `.cursor/rules`: "Nunca usar index como key em listas dinâmicas. Usar ID único."

> **Recomendação:** Gerar ID único ao adicionar recipient (ex: `crypto.randomUUID()` ou contador incremental) e usar como key.

### OBSERVAÇÕES

**[O1] useAuditRules.ts — `alert_recipients: unknown` (linha 16)**

O tipo `unknown` é tecnicamente aceitável (melhor que `any`, satisfaz m1), mas o schema real do banco provavelmente define isso como `jsonb`. Tipar como `Array<{ type: string; value: string }>` (que é o formato usado no form de Audits.tsx) daria autocomplete e validação em compile-time.

> **Recomendação (baixa prioridade):** Refinar tipo para `Array<{ type: string; value: string }> | null`.

**[O2] TONE_CONFIG duplicado em múltiplas páginas**

`TONE_CONFIG` (com labels e classNames para ok/atencao/alerta/critico) aparece em:
- `SearchPage.tsx` (linhas 35-40)
- `ClientDetailPage.tsx`
- `Index.tsx`

Não é uma violação de checklist, mas viola o princípio DRY do Playbook. Um refactor para `src/lib/constants.ts` ou `src/config/tone.ts` centralizaria a definição.

> **Recomendação (baixa prioridade):** Extrair constantes compartilhadas para arquivo centralizado.

**[O3] useAuditRules.ts — `queryKey` não inclui `limit` (linha 32)**

```ts
queryKey: ["audit-rules", user?.id, page],
```

O `limit` é parâmetro da query mas não está no `queryKey`. Se o componente consumidor mudar o `limit`, o cache retornará dados stale. Atualmente só é usado com `limit=20` fixo (PAGE_SIZE), então o impacto é zero — mas se reutilizado com `limit` diferente, causaria bug.

> **Recomendação (baixa prioridade):** Incluir `limit` no `queryKey` por completude (m5).
